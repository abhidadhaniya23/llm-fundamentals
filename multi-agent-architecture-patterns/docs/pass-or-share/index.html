Review · 2026-11-06 · multi-agent-architecture-patterns/das

Does the DAS multi-agent code follow these contracts?

Mostly yes. It follows the pass, don't share rules well: code owns the record, briefs are small, there is one strict contract per handoff, and other teams get a baton.

It does not follow the page's result contract. There is no shared envelope (status / confidence / evidence_ids / caveats + payload), and nothing checks that the IDs an agent returns are real. That second gap is the one that matters.

What diverges

Where it departs from the page

Tap a gap to see what the page says and what the code does.

1. There is no shared result envelope

Page Every result has the same envelope (status, confidence, evidence_ids, caveats) around a job-specific payload, and echoes the brief's task_id.

Code Each output is a flat, one-off shape. None has confidence, an agent-level status or a task_id. DEBUG_OUT.status is the file's ingestion status, not whether the agent finished. When an agent fails, it raises AgentError and the user gets a generic fallback reply, not a status: "partial" the Coordinator could act on. (das/team.py:31-41, das/runtime.py:68-70)

2. There are no claim checks (evidence_ids)

Page A small message holds the conclusion plus IDs pointing to the proof (Q5).

Code B's evidence is a free-text explanation of up to 1500 characters, with no pointer to the validation-log entry it relied on. batch_id and reason_code are partial claim checks, but nothing lets an auditor follow the evidence back to the record.

3. Hallucinated IDs can pass the output check Most important

Page Twist 5: evidence can be hallucinated, so validation checks that every ID is real.

Code call_debugger_agent and call_search_agent are gateway tools, so Gateway.call adds every ID in the LLM agent's JSON to known_ids. If B invents a BATCH-…, the Coordinator can repeat it and check_output will accept it. Nothing compares B's batch_id / doc_id / reason_code with the store. Also, ID_PATTERN doesn't match reason codes, so the output check never looks at them. (das/gateway.py:129-130, das/guardrails.py:28)

4. Output schemas are looser than the input schemas

Page Strict where code reads the result.

Code SEARCH_OUT.doc_id and workspace are plain strings, not DOC_ID / WORKSPACE. DEBUG_OUT.batch_id and reason_code aren't held to the BATCH_ID / REASON_CODE patterns, and status has no enum. That's a problem because code makes routing decisions from these fields.

5. There is no caveats field

Page Q4: hedges get lost over summarising hops, so a required field must carry the doubt ("coil not ruled out").

Code Doubts can only go in note or explanation, which are optional or mixed with other prose. Nothing makes an agent state its uncertainty.

6. Briefs name the return shape only loosely

Page The brief carries a task_id and names a versioned contract ("return": "DiagnosisOut v1").

Code "output": "{doc_id, workspace, …}" is prose, and there is no task_id.

7. There is no real front door

Page Q9: an intake step turns open text into a small, fixed list of supported intents.

Code The input guardrails make only an on-topic / off-topic call. The Coordinator LLM routes open text however it likes, and the tool preconditions are the only limit.

8. A token fragment goes into an LLM prompt Low

Page Identity comes from SSO and stays out of the LLM.

Code Baton.user is ctx.user.scope(), which includes token[:12] + "…". That baton becomes C's brief and is also written to the trace. It's a fake placeholder here, but the pattern should go: keep the token out of the brief. (das/store.py:67-68, das/team.py:223)

Next steps

Suggested fixes, by priority

1Check agent results before trusting their IDs. In call_debugger_agent / call_search_agent, compare batch_id (exists and owned by this user), reason_code (in the catalogue) and doc_id (matches the brief) with the store. Don't let agent-produced results add to known_ids; only real system tools and the user's message should.
2Add a shared envelope (task_id, status, confidence, evidence_ids, caveats) around each agent's current output, which becomes the payload.
3Tighten the output schemas to the same patterns and enums the input schemas use.
4Remove the token from Baton.user.
5Optional: add an intent classifier so the Coordinator only sees supported intents.
