Workflows & Agents · hand-rolled, no framework

Seven exercises, and every step is an agent

These are the exercises from Building Effective Agents with LangGraph, with the same pattern shapes. The joke exercises are replaced by an office scenario (a team moving to a new building), and the scaling-laws report and the "3 and 4" calculator stay. They're rebuilt in plain Python on labs/shared.py, with no LangGraph or LangChain.

Workflow

Your code sets the path. LLM calls fill in the steps along it.

The harness · shared.run_agent

An agent is a loop you can read in one screen

  • Tools are plain functions. Their signature and docstring are the description the model reads.
  • The protocol is JSON in the prompt, not a provider's native tool API, so it works the same on Nexus and Claude.
  • validate is how code gets the last word. If an agent skips a check, it gets the error back and tries again.
  • Tool errors are sent back to the model too, so a bad call doesn't crash the run.

Labs 01–05 run two ways

Every step is an agent. Who decides the order?

workflow

Predictable: every run takes the same path, and you can test each step on its own.

Use it when you can write the order down in advance.

agentic

Flexible: the lead agent can skip a step, redo one or ask again with a better brief.

Use it when the next step depends on what the last one returned.

Either way

Code checks the final answer. In agentic mode, code also records what the sub-agents really returned, so the lead can't claim results that never happened.

wf01 · Prompt chaining

A chain of agents, with a gate in code between them

In the notes

Topic → first version → gate (a code check) → improve → polish. Three single calls.

Here

The input is the move team's internal memo, which is vague and full of jargon. It has to become a staff notice that uses the real facts (dates, places, contacts), passes the plain-language checks, says when and who to contact, and is at most 150 words. The model can't check any of that without tools.

Code checks
  • The Drafter must list at least 3 real fact ids.
  • The gate stays in code, as in the notes: a draft with no date or no contact address stops the chain.
  • The Plain-language output must have no jargon and no sentence over 25 words. The Final editor's output must also be complete and at most 150 words.

wf02 · Parallelization

Three writer agents at once, then an agent that checks their facts

In the notes

One topic → three different pieces written in parallel → an aggregator that joins the strings.

Here

The topic is the office move, and the three pieces are what a communications team sends: a staff email (120–200 words, ≥3 facts, a date and a contact), a chat post (≤280 characters) and an FAQ (3–5 Q&As, each answer citing its fact). The aggregator is an agent that checks every fact id with get_fact.

Code checks
  • Each writer's validator checks its length limit, real fact ids, the plain-language rules and, for the email, a date and a contact.
  • Each FAQ answer must end with the id of the fact it is based on.
  • The combined output must have all three headings. dispatch isolates failures, so one writer failing doesn't stop the others.
Try this

Change one fact (say, the move date in O01) while the writers are running. Does the Aggregator spot pieces that disagree?

  • In agentic mode, the employee gets the reply the desk wrote, not the router retelling it.

Code checks
  • The plan has 3–5 sections, and every paper id it uses exists.
  • Each section cites only papers that exist and that this worker read.

# Scaling Laws for Large Language Models

Scaling laws describe how a model's performance changes as we increase its parameters, its training data and the compute spent on it. They have become a main tool for planning large language model (LLM) training. They help decide how big a model should be, how much data it needs, and what performance to expect before an expensive run begins.

This report has four parts:
- the empirical foundations of power-law scaling;
- the compute-optimal training debate and its later refinements;
- whether downstream capabilities scale predictably or emerge abruptly;
- the newer idea of scaling compute at inference time.

The inference-cost argument of [sardana2023] appears in two sections: as a refinement of compute-optimal training, and as context for test-time compute. Some overlap between those sections is intentional.

## Foundations: Empirical Power Laws

The idea that deep learning performance can be predicted from scale started with large empirical surveys. Across machine translation, language modelling, image classification and speech recognition, Hestness et al. found that generalization error falls as a power law of training-set size [hestness2017]. The model size needed to fit the data also grows as a power law of data size [hestness2017]. The exponent of these curves depends mainly on the task domain and is less sensitive to model architecture [hestness2017]. The authors described learning curves as having three regions: a small-data region, a power-law region, and an irreducible-error region [hestness2017].

Kaplan et al. made this concrete for neural language models. They showed that cross-entropy loss follows smooth power laws in model size (counted as non-embedding parameters), dataset size and training compute, over more than seven orders of magnitude [kaplan2020]. Each relationship holds when the other two factors are not a bottleneck [kaplan2020]. Within a wide range, architectural details such as depth versus width matter little [kaplan2020].

Two further findings shaped later practice. First, larger models are more sample-efficient: they reach the same loss with fewer tokens [kaplan2020]. Second, for a fixed compute budget, Kaplan et al. recommended growing model size faster than dataset size and stopping training before convergence [kaplan2020]. This compute-allocation advice favoured large, comparatively under-trained models.

## Compute-Optimal Training and Its Extensions

A central question in scaling is how to divide a fixed compute budget between model size and training data. Hoffmann et al. found that for compute-optimal training, parameters and training tokens should grow in roughly equal proportion as compute increases. A common rule of thumb follows: about 20 training tokens per parameter [hoffmann2022]. Their Chinchilla model had 70B parameters and was trained on about 1.4 trillion tokens. It outperformed the 280B-parameter Gopher trained with the same compute. This showed that many large models of the time, such as Gopher and GPT-3, were undertrained for their size [hoffmann2022].

Later work relaxed two assumptions behind this prescription. The first is that unique data is plentiful. Muennighoff et al. showed that when unique text runs out, training for up to about four epochs on repeated data costs very little compared with unique data [muennighoff2023]. Beyond that point, the value of extra repeated tokens decays toward zero, and with many more repetitions adding compute stops helping. Mixing in code data or relaxing quality filters can stretch a limited text budget [muennighoff2023].

The second assumption is that only training cost matters. Sardana and Frankle argued that total lifetime cost includes both training and inference compute [sardana2023]. When inference demand is high, a smaller model trained on more tokens than the Chinchilla ratio suggests is cheaper overall. This helps explain why recent models are often trained far past 20 tokens per parameter [sardana2023].

## Predictability, Emergence, and Capabilities

A central question for scaling research is whether gains from scale translate into downstream capabilities that can be anticipated. For loss, the evidence for predictability is strong. GPT-4's final training loss was predicted in advance with a power law fitted to much smaller runs using up to 1,000 to 10,000 times less compute [openai2023]. Its pass rate on a subset of the HumanEval coding benchmark was also forecast from small-scale runs [openai2023]. The report nonetheless notes that not every capability was predictable, and some tasks showed unexpected trends [openai2023].

Wei et al. describe a less orderly picture. They call an ability emergent if it is absent in smaller models but present in larger ones. Such abilities sit near random performance at small scale and then appear sharply, so they cannot be predicted by extrapolating from smaller models [wei2022]. Examples include few-shot multi-step arithmetic and chain-of-thought prompting, which helps only beyond a certain model scale [wei2022].

Schaeffer et al. argue that much of this apparent emergence comes from the choice of metric. All-or-nothing measures such as exact-match accuracy can turn smooth underlying improvement into a sudden jump [schaeffer2023]. Under continuous metrics such as token edit distance, performance improves smoothly and predictably with scale [schaeffer2023]. They therefore recommend checking emergence claims against the metric used and the number of models evaluated [schaeffer2023]. Taken together, these works suggest that whether capabilities look predictable depends heavily on how they are measured.

## Scaling Test-Time Compute

Scaling laws have mostly asked how to spend compute during training. A complementary view treats inference-time computation as a second scaling axis, separate from parameters and training data [snell2024]. A model can spend extra compute on a query by revising its answer sequentially or by running a search guided by a verifier, and both approaches can improve output quality [snell2024].

The best way to use this budget depends on how hard the question is. Allocating test-time compute adaptively by question difficulty was more than four times more efficient than a best-of-N baseline [snell2024]. On easier and medium-difficulty questions, a smaller model given extra test-time compute could outperform a much larger model [snell2024]. The advantage has limits. On the hardest questions, scaling pretraining remained more effective, so test-time compute complements parameter scaling but does not fully replace it [snell2024].

These results fit with work that counts inference cost in compute-optimal design. Chinchilla-optimal training ignores the cost of serving a model, but a model's total lifetime cost includes both training and inference compute [sardana2023]. When expected inference demand is high, training a smaller model on more tokens than the Chinchilla ratio suggests lowers total cost [sardana2023]. This helps explain why recent models are often trained far past 20 tokens per parameter [sardana2023].

Taken together, these findings suggest that compute allocation should be planned over the model's whole lifecycle. Smaller, longer-trained models paired with difficulty-aware test-time compute can be an efficient alternative to scaling up parameters, though this has been shown mainly for non-frontier questions.

## Conclusion

Scaling-law research has moved from observing that loss follows power laws [hestness2017, kaplan2020] to prescribing how to spend compute.

- **Training allocation.** Chinchilla's balanced split of parameters and tokens [hoffmann2022] corrected earlier advice to favour very large models.
- **Practical limits.** That prescription has since been adjusted for limited unique data [muennighoff2023] and for inference costs [sardana2023].
- **Predictability.** Loss can be forecast reliably [openai2023]. Downstream abilities are less certain: they may look emergent [wei2022] or smooth [schaeffer2023], depending on the metric.
- **Inference compute.** Test-time compute adds a further scaling axis [snell2024]. This suggests future scaling laws will need to cover a model's whole lifecycle, not just pretraining.

Scaling laws have mostly asked how to spend compute during training. Is wf05's workflow loop an agent?

No. The for loop and the "approved?" check are code. What's inside the loop are two agents. In agentic mode, the loop moves into the Writer agent.

Why not just trust the agent's final answer?

Because it can skip its tools. In the test runs, wf04 workers cited papers they hadn't read. validate sent them back to read before their sections were accepted.

What would LangGraph give you that these labs don't have?

Infrastructure, not patterns: checkpoints and memory, streaming, human-in-the-loop pauses, deployment. For checkpoints you could write your own; see 01b_sequential_agents_hardened.py.

One line to remember
The pattern

The pattern is the order of the steps: chain, fan out, route, plan, loop. It's plain code.

The agent

The agent is a loop inside a step: model, tool, result, repeat. It's about 50 lines of Python.

Give a step an agent when it needs tools to get the answer right. Then check the answer in code.
