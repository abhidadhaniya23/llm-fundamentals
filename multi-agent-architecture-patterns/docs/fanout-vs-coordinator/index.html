Fan-out vs Coordinator
← → or Space to move · F for full screen
Multi-agent patterns · Concept

Same question, different person answering it

Both patterns answer one question: how should this work be split? What differs is who answers it, and when. Everything else on this page follows from that.

Fan-out

You decide the split once, when you build it. Every run sends the same pieces out in parallel and merges what comes back.

Coordinator & specialist

A model decides the split on every run. It reads each result and chooses what to do next.

The one idea that makes it click

Who decides the split, and when

Who decides the splitWhen
Fan-outYou, the designerOnce, when you build it
CoordinatorThe coordinator modelOn every run, for each input

The agents in a fan-out still do real work. They just don't decide what work exists. You did.

Pattern · Fan-out

Scatter, gather, done

  • No model decides the split. It's a loop.
  • Workers are usually the same prompt with different input.
  • It runs once: scatter, gather, done.
Pattern · Coordinator & specialist

Each step depends on what the last one found

  • Nobody could list these steps before reading the ticket. The coordinator works them out as it goes.
  • Specialists are genuinely different: their own prompts, tools and data.
  • It loops until the coordinator decides it's done.
Fan-out · the step people forget

Who merges in a fan-out?

Fan-out only scatters the work. Something you add on purpose combines it: a merge step that runs once, after every worker has finished.

Prefer this

Plain code

Fail if any check fails. Average 3 judge scores. Deduplicate and rank search hits.

Cheap, predictable and testable. Needs structured worker output.

When outputs are free text

One more model call

Turn 40 transcript summaries into "top 5 complaint themes".

Flexible, but it can smooth over a disagreement or add a claim no worker made.

Not a coordinator

The merge step doesn't decide

It doesn't choose what runs or loop. Once it says "these disagree, rerun worker B", it has become a coordinator.

In a fan-out, the quality of the final answer depends mostly on the merge step. Decide up front what happens on conflict.

The question that comes up every time

"Can't a coordinator just do this with subagents?"

Yes, it can. The real question is whether you need a model to make that decision every time.

Runs vary

Some days it decides accessibility isn't relevant and skips it. For a compliance check, that's a bug.

Extra tokens

You pay for a model to rediscover "check these 5" on every run.

Context bloat

Every result passes through the coordinator's context.

Harder testing

You can't check "did all 5 run?" without reading its reasoning.

Fan-out is a coordinator whose decision never changes, written down as code.

Rule of thumb

If you can write the split as a for loop, fan out

If step 2 depends on what step 1 found, use a coordinator.

Fan out
  • Check one letter against 5 policies
  • Summarise 40 call transcripts
  • Translate a notice into 6 languages
  • Search the policy store, the FAQ and old tickets at once
Coordinator earns its cost
  • "Check the contracts that mention the new clause." Which ones, and how many? Something has to look first.
  • "Investigate this incident." It can't know which specialist matters until it sees the first result.
  • "Why did complaints rise in Q3?" The second question comes from the first answer.

The coordinator decides, fan-out does the bulk work

This is the most common shape in real systems. The decisions that depend on the input stay with the model. The repetitive part runs as a plain fan-out.

Zoom out

Four questions every multi-agent design answers

  1. Who decides the steps? You, or a model.
  2. How do the steps relate? Parallel, or one after another.
  3. Who combines the results? Code, or a model.
  4. Who decides it's done? Fixed, or a model.

Check yourself

Which pattern is this?

A router sends each ticket to one of 5 queues.

Router, not coordinator. It makes one decision with no loop and never reads a result back.

Researcher, then writer, then editor.

Pipeline. The order is fixed in code. Nothing is decided at runtime and nothing runs in parallel.

A coordinator always calls all 4 specialists in the same order.

A pipeline in disguise. The decision never changes, so drop the coordinator and save the calls.

Fan out to 5 agents, but agent 3 needs agent 1's output.

Not a fan-out. That dependency makes it at least partly sequential.

One line to remember
Fan-out = standing procedure

You wrote down the split once. Everyone follows it every time.

Coordinator = manager on duty

Looks at each case and decides who to call next. Flexible, but it costs more and runs differently each time.

If you can write the split as a for loop, fan out. Pay for a coordinator only when the work changes from one input to the next.
