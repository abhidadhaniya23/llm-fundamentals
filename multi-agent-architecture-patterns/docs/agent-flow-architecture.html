1

Priya · Finance Analyst

"I uploaded 20 invoices yesterday but I can't find invoice 1234 in Finance. If it got rejected, tell me why and get me access to the Compliance archive to re-upload it there."

Chat UI

Web portal / Teams bot. Shows answers, status cards, file upload and the approval status of requests.

2

API gateway + SSO

Authenticates the user (OIDC / Azure AD), attaches her token with roles (Finance-Reader, Finance-Uploader), rate limits.

Input guardrails

Prompt-injection & jailbreak detection, PII redaction, topic filter (archive questions only), size checks on uploaded files.

8

Output guardrails

Only show records the user may see: mask PII, block hallucinated record ids (answer must cite a real record), then return the reply to the Chat UI.

2 · Orchestration
3

Coordinator / Supervisor agent

Reads the request, splits it into tasks, routes them, keeps conversation state and merges the Manager-style results into one answer.

Intent & planner

Three intents: (a) locate invoice 1234, (b) explain the rejection, (c) obtain access + re-upload to Compliance. Plan: a → b → c.

Router

A and B are independent → run in parallel. C only after b returns a reason code. D only on a system fault.

Session memory

Short-term context (batch id, invoice id, open ticket) so follow-ups like "is it approved yet?" work.

Response composer

Stitches A + B into one clear reply with next steps and citations to real records.

Owns: Priya's reply for (a) and (b). Does not own: writes into another team's system — access and re-upload leave via a Handoff.

3 · Manager-called subagents (control returns)
4

A · Search & retrieval agent

Hybrid search over the Finance archive: exact metadata match + semantic search on OCR text.

  • Goal: confirm whether 1234 exists in Priya's Finance workspace.
  • Output: {doc_id, workspace, exists, has_access}
  • Scope: no access requests, no uploads, never replies to Priya.
search_archive()get_record()
→ "1234 is not in the Finance archive."
5

B · DebuggerAgent

Reads yesterday's ingestion batch: per-file status and validation result, then turns reason codes into plain language.

  • Goal: find 1234's status in the batch and why it failed.
  • Output: {batch_id, status, reason_code, fault:bool}
  • Scope: no re-upload, no access request, never replies to Priya.
get_batch_status()get_validation_log()get_reason_code_doc()
→ "19/20 archived; 1234 rejected — missing VAT id / belongs to Compliance class."
⇄ CONSULT (bounded)

B may ask A one question only: exists(doc_id, workspace) → {exists} — e.g. to re-check after a late sync. No free text, no actions, and every consult is reported upward in the result payload so the Coordinator keeps the full picture.

⚠ Silent-drift spot: the DebuggerAgent answering Priya directly ("your invoice was rejected, I'll re-upload it") instead of returning its JSON. That turns an M call into an unplanned H — the Coordinator loses the thread and the reply is never composed. Guard: no messaging tool in B's tool set.
4 · Handoff targets (control moves)
6

C · Access & policy agent (Compliance team owns it)

Checks Priya's entitlements against archive policy; if she lacks Compliance write access, raises an approval request and owns it to completion.

check_entitlement()create_access_request()
→ "Request REQ-xxxx sent to the data owner."
M↕ after approval, inside the Compliance trust domain
7

D · Re-upload agent

Pre-validates the corrected file against the same rules, then uploads it to the Compliance archive and confirms.

prevalidate()upload_record()
→ "1234 archived in Compliance."

E · Developer / Platform team

Humans. Taken only when B's reason code is a system fault (archive down, migration mismatch) rather than a user-fixable validation error.

open_incident()
→ owns the ticket from here; the bot is done.
The handoff baton — what actually transfers on an H arrow: context package (invoice_id, batch_id, reason_code, Priya's identity and token scope) + ownership of the reply + who notifies her next. The Coordinator states this explicitly, then stops tracking the flow.
5 · Tool layer

Tool gateway (MCP / API layer)

One controlled door to the enterprise systems. Calls run on behalf of the user (her token, never a super-user account), each subagent is granted only the tools in its own brief (least privilege — A has no create_access_request(), B has no upload_record()), inputs are schema-validated, and write actions need explicit confirmation.

6 · Data & enterprise systems

Archive storage

Object store (WORM / immutable) with separate Finance and Compliance archives and retention rules.

Metadata & search index

Record metadata (invoice no., vendor, date, uploader) + vector index on OCR text.

Ingestion pipeline

Upload → OCR → classification → validation rules → archive. Writes status + reason codes to the validation log.

IAM / entitlements

Roles and groups (RBAC / ABAC) per archive: read, upload, admin.

Policy knowledge base

Archival & retention rules, rejection-code catalogue (RAG source for the plain-language explanations).

ITSM / access workflow

e.g. ServiceNow: access-request ticket, approval routing, notification.
