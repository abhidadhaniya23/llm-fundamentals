2Three call types

M · Manager-style call

A tool whose fn runs another Agent.run() and returns its output. Control returns to the caller.

Coordinator → A, Coordinator → B, C → D. Tool.kind = "agent"

das/team.py · call_search_agent, call_debugger_agent, call_reupload_agent

H · Handoff

A tool that appends a Baton to DASChatbot.pending_handoffs and returns at once. Control and ownership move; the Coordinator never sees the outcome.

Coordinator → C. Tool.kind = "handoff"

das/team.py · _hand_off · das/runtime.py · _dispatch_handoffs

Consult

B asks A one structured question (consult_search_exists), allowed once (consult_once), reported upward in B's consults.

Tool.kind = "consult"

das/tools.py · consult_search_exists, consult_once

1How to read this diagram

Layout

  • Columns are lifelines. The box at the top gives the participant and its file; the dashed line under it is that participant over time.
  • Time runs top to bottom. The number on each arrow is its step number (see the Step-by-step tab).
  • Shaded bands are phases. The band's name is in its top-right corner.

Arrows

  • Caller → callee. The arrowhead points at whoever receives the call, result or message.
  • Line style shows the kind of call. See the legend: blue = Manager call (control returns), dashed grey = result, thick purple = handoff (control moves), teal = consult, orange = write tool, dotted = LLM call, green = guardrail or message to Priya.
  • A loop back into the same column is an internal step (2 SSO, 7 parallel dispatch).

Things to notice

  • Parallel work is drawn in sequence. Steps 8–10 (A) and 11–16 (B) run at the same time; they are only stacked so they are readable.
  • After the handoff (18), the Coordinator's only remaining arrow is its reply (19). From 22 on, C·Access does the work and sends message 2 itself.
  • Not drawn: the LLM turns of A–D between their tool calls, and the Gateway.call checks inside each tool arrow.

2Agent output schemas

Built with obj(), so additionalProperties: false. Agent._loop validates the final answer and allows one repair.

SEARCH_OUT · A·Search

required doc_id, workspace, exists: bool, has_access: bool; optional note.das/team.py

DEBUG_OUT · B·Debugger

required batch_id: str|null, status, reason_code: str|null, fault: bool, explanation (≤1500); optional consults: array.das/team.py

ACCESS_OUT · C·Access

required request_id: str|null, access ∈ {granted, already_had, pending, rejected}, reupload_status, notified: bool.das/team.py

REUPLOAD_OUT · D·Reupload

required doc_id, workspace, prevalidation ∈ {passed, failed}, status ∈ {archived, not_uploaded}; optional detail.das/team.py

5Routing preconditions

access_handoff_allowed

B returned a reason_code; fault is false; baton reason_code and batch_id equal B's; invoice_id equals the session's.das/team.py

reupload_allowed

The request exists, belongs to the user, is approved, and is for the target workspace.das/team.py

upload_allowed

prevalidate passed for this doc in this run, and the user now has upload access.das/tools.py

consult_once

Only one consult per DebuggerAgent run.das/tools.py

notify_once

Only one notification per handoff.das/team.py
