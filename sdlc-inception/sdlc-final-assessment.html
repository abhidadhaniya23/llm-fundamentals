SDLC: From Idea to Done - Final assessment

Covers the whole course, from the definition of SDLC through to traceability. Answer each question first, then click it to check yourself.

This is the end-of-course assessment. It is deliberately broader than the section recap: it covers every concept topic in order, including the parts that are easy to skip - the five delivery models, what Waterfall buys you, and the detail of the dev cycle.

1. SDLC foundations

1. What does SDLC stand for, and what does it give a team?

Software Development Life Cycle: a structured process to plan, build, test, deliver and maintain software, so the team builds the right product, builds it right, and delivers it predictably.

What it replaces:

  • Shared understanding, instead of unclear requirements
  • Predictable delivery, instead of surprise delays
  • Quality built in, instead of defects found late
  • Traceability, instead of "who decided this?"
  • A repeatable team process, instead of hero developers
2. Name the seven SDLC phases in order, and what each one answers.
  • Requirements - what, and for whom
  • Analysis - feasibility and risk
  • Design - architecture
  • Implementation - code
  • Testing - verification
  • Deployment - release
  • Maintenance - operate and improve

Requirements and analysis define the problem; design and implementation create the solution; testing, deployment and maintenance keep it alive.

3. "The phases never disappear." What does that mean across delivery models?

Whether you run Waterfall, Agile or anything between, the same seven activities happen. Only their order and their size change.

Waterfall does each one once, in sequence, at full size. Agile does all seven inside every sprint, in miniature. Nobody skips design or testing - they either do it deliberately or do it accidentally.

4. What artifact does each phase produce, and why does that matter?
  • Requirements: vision, epics, stories with acceptance criteria
  • Analysis: feasibility notes, risk list, estimates
  • Design: architecture diagram, interface and data contracts
  • Implementation: working code and a reviewed pull request
  • Testing: test cases traced to the acceptance criteria, and test reports
  • Deployment: a released increment, runbook, release notes
  • Maintenance: monitoring, defect reports, change requests

If a phase produces no artifact, you cannot show it happened - and you cannot trace a decision back to it later.

5. Name the six roles and the handover each one owns.
  • Product Owner: vision, priorities, acceptance - owns Idea → Epic
  • Business Analyst: requirements, stories - owns Epic → Story
  • Architect: solution design, NFRs - owns Story → Plan
  • Developer: plan, code, unit tests - owns Plan → Code
  • QA / Tester: test strategy, verification - owns Code → Test
  • Release / Ops: deployment, operations - owns Test → Live
6. "A role is not a job title." Explain.

A role is who is accountable when that artifact is wrong, not what is written on someone's contract.

So: one owner per artifact, not one owner per person. In a small team one person wears several hats, and that is fine - as long as each artifact still has exactly one name against it. And AI assists a role; it never owns the accountability.

2. Delivery models and choosing between them

7. Name the five SDLC models, with one line each.
  • Waterfall - sequential, phase by phase, each signed off
  • V-Model - Waterfall with a test level mirrored to each design level
  • Iterative - build in pieces, refine each round
  • Spiral - risk-driven iterations
  • Agile - short cycles, working software early, change welcome
8. What four forces do you weigh when choosing a model?
  • Predictability - how fixed is the scope?
  • Risk control - how early do you need feedback?
  • Speed of learning - how short must the loop be?
  • Cost of change - how late is too late to change your mind?

The honest summary: choose by how much you already know. Certainty favours Waterfall; uncertainty favours Agile.

9. How does Waterfall work, and what does it cost you?

Phases run in sequence and each is signed off before the next starts. Change after sign-off is a change request.

What it costs:

  • Feedback arrives only at acceptance testing
  • Change after sign-off is expensive
  • Testing gets squeezed at the end
  • Risk is discovered late
  • Handovers lose context
10. What does Waterfall buy you? Name its genuine strengths.

Waterfall is not bad - it is built for a stable problem. It buys:

  • Clear scope and a plan you can contract on
  • Strong documentation
  • Easy management with fixed-price suppliers
  • A good fit for stable, regulated work
  • Predictable staffing

The failure is not using Waterfall. The failure is using it on a problem nobody understands yet.

11. What is the V-Model, and where is it still common?

Waterfall with a test level mirrored to each design level - unit tests against detailed design, integration tests against architecture, acceptance tests against requirements.

Still common in regulated and automotive contexts, where every requirement must have a demonstrable matching test.

12. Compare Waterfall and Agile across the seven dimensions.
  • Planning: upfront and complete / rolling, just in time
  • Delivery: once, at the end / every sprint
  • Change: a change request / welcome, reprioritise
  • Feedback: late, at acceptance testing / continuous, at sprint review
  • Documentation: heavy / lightweight and living
  • Risk: discovered late / discovered early
  • Best for: stable, fixed scope / uncertain, evolving scope
13. Under each model, when does the first real user feedback arrive?

Waterfall: not until acceptance testing, near the end - on a 30-week project, around week 28. A misunderstanding made in the requirements phase stays invisible until then, which is exactly why it is so expensive to fix.

Agile: at the first sprint review, around week 4, and every two weeks after. The same total work, but the feedback loop is weeks rather than months.

14. Name the four Agile Manifesto values. What does "over" mean?
  • Individuals and interactions over processes and tools
  • Working software over comprehensive documentation
  • Customer collaboration over contract negotiation
  • Responding to change over following a plan

"Over" does not mean "instead of". The items on the right still have value - they are just not what you optimise for when the two conflict.

3. Inception

15. What is an agile inception, how long should it take, and what is the real output?

A collaborative project-launch workshop run at the start of delivery, in 1 to 5 days, uniting stakeholders, product owners and the team to agree a shared vision, scope and plan.

Days, not months. And the output is not a document set - it is a room full of people who agree on the same MVP. A team that produces every artifact but changes no outcome has failed.

16. Name the ten activities of the Agile Inception Deck.
  • Why are we here? (vision / business case)
  • The elevator pitch
  • The product box (or cover story)
  • The NOT list (out of scope)
  • User personas and roles
  • Feature discovery and user story mapping
  • Technical solutions and architecture
  • What keeps us up at night? (risk assessment)
  • Trade-off sliders (scope vs time vs budget vs quality)
  • Sizing and the first release (MVP definition)
17. For three inception activities, name the data collected and the expected outcome.
  • Why are we here? Data: business drivers, problem statement, KPIs, strategic objectives. Outcome: shared understanding of why the project exists and what success looks like.
  • NOT list. Data: deferred features, future-phase ideas, non-goals. Outcome: scope creep prevented, false consensus eliminated.
  • Trade-off sliders. Data: fixed-vs-flexible positions for scope, cost, time, quality, partners. Outcome: agreed rules of engagement for future trade-off decisions.

The pattern: every activity has a deliverable. Nothing is a discussion that ends in nothing.

18. Which artifact does each inception activity produce?
  • Stakeholder identification: stakeholder map
  • Persona creation: personas (plus empathy map)
  • Current-state mapping: as-is journey map
  • Problem definition: problem statement / "How might we" questions
  • Visioning and goal setting: product vision, goals and success metrics
  • Scope boundaries: in / out of scope, the NOT list
  • Future-state design: to-be journey map and service blueprint
  • Feature discovery: user story map
  • Release slicing: MVP definition and release plan
  • Epic definition: epics, cut from the map's release slices
  • Risk identification: RAID log
19. What is the difference between an output and an outcome?

An output is a thing you shipped. An outcome is a measurable change in user or business behaviour.

"The system is deployed" is an output. "Average handling time drops from 25 days to 5" is an outcome. Inception agrees the outcomes, because outputs are not success.

20. What belongs on a NOT list, and why is it one of the highest-value hours of the week?

Everything deliberately not delivered in this horizon: deferred features, future-phase ideas and explicit non-goals.

It is high value because it kills false consensus. Stakeholders who all nodded at the vision often had different products in their heads; the NOT list is where that surfaces - in a workshop, not in sprint 9.

21. What is an MVP, and what is a learning goal?

An MVP is the smallest thing you build in order to learn whether it is worth continuing. It is not "version one with fewer features", and it is not a prototype.

Every MVP therefore carries learning goals - the assumptions it is designed to test, written as questions. If you cannot say what you would learn, you have a release, not an MVP.

22. How does a risk identified at inception become work?

Each risk is named, given a severity and probability, and paired with a mitigation - and that mitigation becomes an epic or a story with an owner.

That is how inception feeds the backlog: the epic map is not invented, it is derived from scope plus risks. A risk with no epic is a risk nobody owns.

23. What is a proto-persona, and what is the risk of using one?

A persona built from the team's own knowledge - a process document and a workshop - rather than from user research.

A legitimate starting point when there is no research, provided it is labelled as such. The risk is assumptions hardening into fact: nobody remembers which parts were evidence. Mark every unvalidated figure and validate it early.

24. Name the traceability ID chain carried through the inception artifacts.

Stakeholder → persona → pain point → as-is step → goal / capability → to-be step → story-map card → epic → user story.

Typically SH-, P-, PP-, A-, G- / C-, T-, S-, E-, US-.

4. Epic map, estimation and epics

25. What is an epic map, and what is it used for?

A visual map of all epics, arranged by capability left to right and by priority or release top to bottom. It shows the whole product at a glance, instead of 300 loose stories, and is used to slice releases horizontally and to make gaps and dependencies visible.

26. Which estimation technique is used for epics, and which for stories?
  • Epics: T-shirt sizing (XS, S, M, L, XL)
  • Stories: story points with Planning Poker (1, 2, 3, 5, 8, 13)

An XL epic is a signal to split. Story points measure complexity, effort and uncertainty relative to a reference story - they are not hours.

27. What do you do with an epic you cannot estimate confidently?

Record the low confidence rather than hiding it behind a number, and ask what the estimate depends on - usually an unproven capability or data that does not exist yet.

Then plan a spike early to retire the uncertainty, flag the epic as a risk, and give a confidence range instead of a single figure. An estimate nobody believes is worse than an admitted unknown.

28. What is an epic, and where does it sit in the hierarchy?

A large body of work that delivers one clear business outcome, too big for a single sprint, broken down into stories.

Hierarchy: Initiative / Theme → Epic → Story → Task.

29. Why do epics matter?

Alignment, prioritisation, roadmap and funding, traceability (idea to epic to story to commit to test), and scope control. They are the level at which the business can actually have a conversation about value.

30. Name the sections of a good epic.

Title, problem / context, outcome and success metrics, users / personas, scope and out of scope, epic acceptance criteria, NFRs, dependencies and risks, size, milestone.

31. How do you tell an epic from a story, and why does an epic need an out-of-scope section?

An epic delivers a whole capability across several sprints; a story is one slice that fits inside a single sprint. If it cannot be finished in one sprint, it is an epic.

It needs an out-of-scope section because neighbouring epics overlap - without a boundary, two teams either build the same thing twice or both assume the other is doing it. Naming what the epic does not cover, and which epic covers it instead, is the NOT list applied one level down.

5. Stories

32. What is the user story format, and what are the 3 Cs?

As a persona I want capability so that benefit. The "so that" is the most important part - it is the only bit that states the value.

The 3 Cs: Card (short description), Conversation (the discussion it triggers), Confirmation (acceptance criteria).

33. What does INVEST stand for, and what do you do when a story fails one of the letters?
  • Independent, Negotiable, Valuable, Estimable, Small, Testable

Fails Estimable: run a spike. Fails Small: split it. Fails Testable: the acceptance criteria are missing. Fails Valuable: it is probably a task, not a story.

34. What is Given / When / Then used for, and what must the criteria cover?

Acceptance criteria - written so each one becomes a test case directly.

A complete set covers the happy path, edge cases (empty, partial, duplicate, boundary), errors (what the user sees when a dependency fails), and the negative case - what must not happen, such as nothing being sent or saved until a person approves. The negative case is the one teams forget, and usually the one that matters for safety.

35. When should a story be split, and what are the SPIDR patterns?

At 13 points or more, or whenever it cannot finish inside one sprint.

SPIDR: Spike, Path, Interface, Data, Rules. Also useful: by workflow step, and happy path first.

36. Where does slicing happen?

At two levels - epic and story. It is not a single step.

  • Epic level. Release slices are drawn on the story map: each horizontal line cuts through every journey step and becomes an MVP or a release. Epics are cut from those slices, which is what makes them vertical by design.
  • Story level. Stories are split again inside each epic, using SPIDR or by workflow step, data type or business rule.
37. Why must you never slice by technical layer?

Because "the database story", "the API story" and "the UI story" each deliver nothing on their own. None can be demonstrated, none can be accepted, and none can be dropped without breaking the others - so you lose the ability to reprioritise, which is the whole point of a backlog.

Every epic and every story must deliver something a user can see working.

38. How do you cross-check an epic's size against its stories?

Add the stories' points and divide by velocity: that gives the number of sprints, which should match the epic's T-shirt size.

For example six stories totalling 34 points, at a velocity of about 20, is roughly two sprints - consistent with an L. If the two disagree, either the epic is mis-sized or stories are missing.

39. What is the difference between the Definition of Ready and the Definition of Done?

DoR protects developers from vague stories: story format, Given/When/Then criteria, NFRs identified, estimated, dependencies known, small enough.

DoD protects users from half-done work: reviewed PR merged, criteria pass, tests green, no critical findings, quality gates pass, docs updated, Product Owner accepted.

6. The dev cycle: Plan, Code, Review, Test

40. Put the dev cycle in order, and name the human gate at each step.
  • Story (Ready) - passes the DoR
  • Plan (design and tasks) - gate: the tech lead approves
  • Code (small diffs) - gate: the developer steers and checks each phase
  • Review - gate: a human reviewer approves the pull request
  • Test (from the criteria) - gate: QA confirms the tests prove the criteria
  • Done - gate: the Product Owner accepts

AI assists every step; a person approves every gate.

41. Why plan before generating, and what must a plan contain?

A plan is the contract you give the agent. It names the files, the phases and the tests; the agent follows it and you check each phase against it.

Building it: understand the story and its acceptance criteria, explore the codebase to see what exists and what changes, then break the work into phases and name the risks and test strategy. Fifteen minutes of planning saves hours of rework.

42. Why generate in small steps, and what is wrong with a 1,000-line commit?

Because small diffs are reviewable diffs. A thousand-line change gets approved without being read; a hundred-line change gets reviewed.

So: implement phase by phase from the approved plan, work on a feature branch with small focused commits, and write tests alongside the code or before it. A 1,000-line commit means nobody really reviewed it - the gate was technically passed and actually skipped.

43. What is the split between an AI review and a human review?

AI finds patterns; humans find intent.

The AI review is good at consistency and known pitfalls, and it should run first so the human is not spending attention on them. The human review knows what the Product Owner actually meant - which no model can check. Human approval is mandatory, and a gate is never bypassed.

44. In what order should a review check things?

Acceptance criteria first - does this actually do what the story asked? Only then design, readability, tests, security and performance.

Reviews that start with style spend all their attention there and approve code that solves the wrong problem.

45. Why must tests come from the acceptance criteria rather than from the code?

Otherwise the AI is testing its own homework: tests written from the code prove only that the code does what it does, whatever that is. That is not evidence, it is a tautology.

Derive tests from the criteria, then work outwards: unit, then integration, then end to end.

46. What does test coverage actually tell you?

Coverage is a hint, not proof. It tells you which lines were executed, not whether the behaviour is right.

100% coverage can still miss every edge case that matters - and a suite derived from the acceptance criteria at 70% is worth more than a generated suite at 100%.

47. Which AI skill supports each step, and who is the human gate?
  • Idea → Vision: idea-to-vision - Product Owner
  • Vision → Epic: epic-creation - Product Owner
  • Epic → Stories: story-mode - refinement
  • Story → Plan: plan-mode - tech lead
  • Plan → Code: code-generation - developer
  • Code → Review: review-mode - reviewer

The skill does the typing. The gate is where the thinking shows up.

48. Is rework a failure?

No - rework is normal, and the loop back from review to code exists for exactly that reason.

What is not normal is discovering the need for rework after the review gate. That means the gate did not do its job, and the cost multiplies the further downstream it surfaces.

49. Name the three phases of the AI-first development process, and the artifact each one produces.
  • Think First → an implementation plan you review and approve
  • Build Small → code and tests, one phase at a time
  • Focus on Quality → clean code and tests in the repo

It is the same dev cycle as Plan / Code / Review / Test, expressed as the habits you follow at the keyboard.

50. Walk through "Think First". What is the failure mode it exists to prevent?

Explain the requirements → let the AI ask clarifying questions → review and refine the implementation plan.

It exists to prevent the most common failure in AI-assisted work: a one-line prompt turning straight into code. The clarifying questions are not a formality - they are where the gaps in your own understanding surface. The plan is approved before any code exists.

51. What is the inner loop in "Build Small", and how often does it run?
  • Ask the AI to implement one step of the plan
  • Verify it has actually run the tests
  • Review the code and tests against the plan
  • Commit locally

It repeats for each phase in the plan, not once for the whole story. That cadence is what keeps diffs small enough to genuinely review, and it gives you a local commit to fall back to when a phase goes wrong.

52. Why is the step "verify that it has run the tests" rather than "run the tests"?

Because an agent can report success without having executed anything. A confident summary is not evidence.

Open the actual test output and check it ran, and that it ran the tests you expected. Trust the evidence, not the claim - the same principle as "do not let it test its own homework", applied one level up.

53. What are the four steps of "Focus on Quality", and which one is skipped most often?
  • Code review and refactor
  • Run all tests
  • Test manually
  • Push into the repo

Test manually is the one that gets skipped, because the tests are green and it feels redundant. It is not: green tests prove the cases you thought of, and using the thing yourself is how you find the ones you did not. Note also that refactoring comes before the final test run, not after.

7. Sprints, milestones and traceability

54. Name the five sprint ceremonies and where they sit in a two-week sprint.
  • Sprint planning (day 1): pick stories, set the goal
  • Daily stand-up (every day): sync and surface blockers
  • Refinement (mid-sprint): prepare the next sprint's stories to the DoR
  • Sprint review (day 10): demo working software, get feedback
  • Retrospective (day 10): improve how the team works

The sprint is a fixed, protected box of time. Scope can change between sprints, never inside one.

55. What is velocity, what is capacity, and what must you never do with velocity?

Velocity: story points completed per sprint, averaged over the last three. Capacity: people-days actually available this sprint.

Velocity tells this team how much to pull into the next sprint and says nothing about another team. Never use it as a performance metric, and never compare it across teams - both guarantee inflated estimates within two sprints.

56. What does a burn-up chart show that a burn-down does not?

A burn-up plots the completed line and the total-scope line together, so scope growth is visible as a rising ceiling rather than hidden inside a flattening curve.

If the team is delivering steadily but the gap is not closing, the problem is scope, not pace - and only the burn-up shows you that.

57. What is a milestone, and what must every milestone have?

A business checkpoint - not a date on its own. Every milestone needs a goal, a scope of users, and exit criteria you can objectively test.

A common progression is MVP (prove the value, often on replayed data), Pilot (real users, limited group), GA (everyone, fully auditable). "End of Q3" is not an exit criterion.

58. What determines the order of epics across milestones?
  • Dependency: anything other epics need must come first
  • Risk: the riskiest assumption is tested as early as possible, so failure is cheap
  • Exposure: any control protecting a real user - review, approval, permissions, privacy - must land before the milestone that first puts real users in front of the system

A safeguard scheduled after the pilot is a safeguard that arrived too late.

59. Why do platform and enabler epics cluster in the MVP, and what is the trap?

Because the shared foundations - connectors and integrations, identity, data access, the review and approval path - must exist before any user-facing epic can be finished.

The trap: a milestone full of platform work delivers nothing visible. Pair each enabler with the first feature that proves it, and keep the MVP honest - it must still demonstrate something to a user.

60. What does traceability give you, and why does it make AI assistance safe?

Every artifact links to the one before it: Idea → Vision → Epic → Story → Plan → Commit / PR → Tests → Done.

Anyone - an auditor, a new joiner, the team in six months - can walk backwards from a line of code to the problem that justified it. It makes AI assistance safe because each step has a written input and a named approver: the chain, not the model, is what you trust.

Synthesis

61. Across the whole lifecycle, where are the human gates - and what is the one rule?

Vision (PO), epic (PO), stories (refinement), plan (tech lead), code (developer), review (reviewer), test (QA), done (PO).

The rule: AI prepares the evidence; people make the decisions. AI accelerates every step, and never owns one.

62. What stays with people, even when AI accelerates every step?

Accountability. Speed changes; responsibility does not. Every gate is a named person, and "the AI wrote it" has never been an acceptable answer to "why does this code exist?".

63. Retro: where did AI help most, where did it get it wrong, and who caught it?

An open question for your team. Typically AI finds consistency issues and known pitfalls, while humans find "this isn't what the Product Owner meant" - which is exactly the split the gates are designed around.
